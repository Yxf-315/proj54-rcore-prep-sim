## 1. 先搞清楚：这个赛题要交什么

赛题描述的核心是：围绕操作系统课程实验，从"使用 OS / 分析 OS / 实现 OS / 扩展 OS"等维度，
设计**实验内容与比赛项目指导教程**，让学生更好地理解 OS。赛题仓库明确列出的交付物是三类：

| 交付物 | 说明 | 本项目对应 |
| --- | --- | --- |
| **实验指导文档** | 面向学生的实验教程：目标、背景、步骤、思考题 | [`docs/lab-guide.md`](lab-guide.md) |
| **使用说明文档** | 工具怎么装、怎么用、参数与 rCore 对照 | [`docs/usage.md`](usage.md)（另导出 PDF） |
| **实验用的测试用例** | 可自动判定的测例 | `memlab --check cases`（8 个用例）+ `cargo test`（43 项） |
| **实验参考实现** | 可运行的完整实现 | 本仓库 `src/`，零依赖 `cargo run` |

也就是说：**不是交一个"操作系统"，而是交一套"能教、能练、能测"的课程实验。**
评委看重的是教学价值、可复现性与独立完成度，而不是内核规模。

## 2. 全国赛要提交的材料

### 2.1 初赛（作品提交截止日：6 月 30 日）

初赛作品必须包括：

1. **源代码**：完整工程、有注释（中英文均可）、辅助编译文件；
2. **设计方案文档**：选题背景、需求分析、总体设计、关键实现、测试情况、创新点；
3. **进展汇报幻灯片**（PPT/PDF）；
4. **作品演示视频**；
5. 全部提交到大赛指定托管平台，并**展现完整的开发过程**。

### 2.2 决赛（阶段性提交 8 月 12 日；最终提交 8 月 18 日；答辩 8 月 19 日）

在初赛材料基础上继续迭代，提交最终源代码、设计文档、幻灯片、演示视频，并参加**现场答辩**。
决赛结束后，最终版本作品（源代码、文档、视频等）需**保持开源可访问**。

### 2.3 官方明确强调的两点

- **过程性**：初赛阶段要求 **不少于 8 次提交过程记录**，通过提交次数、提交内容、成果演示
  等可客观/量化评价的内容，真实展现研发能力；
- **独立性**：需说明"非本队完成的已有内容"，引用他人代码/设计必须标注。

## 4. 评分维度 → 本项目的证据

## 5. 文档怎么写才像"课程实验"而不是"课程作业"

设计文档建议按下面的骨架写（本仓库 `docs/design.md` 已按此组织）：

1. 选题背景：课程实验的痛点（不可观察、难调试、所有权与内核脱节）；
2. 需求分析：用户画像、使用场景、功能/非功能需求；
3. 总体设计：架构图、模块职责、数据流；
4. 关键实现：数据结构、核心流程、与 rCore 源码的对照表；
5. 测试方案：单元/集成/手工，覆盖了哪些错误路径；
6. 教学验证：在几名学生身上试用、反馈、改进（**有数据最好**）；
7. 创新点与局限；
8. 复现步骤与依赖说明。

> 加分项：附一节"在真实课堂中的试用记录"——多少人用、花了多久、卡在哪、
> 你们怎么改。评委很吃这一套，因为它证明实验"能教"。

## 6. Git 提交计划（满足"≥8 次过程记录"）

不要最后一次性 `git add .` 提交。按功能切片，每次提交能独立编译：

| # | 提交信息（示例） | 内容 |
| --- | --- | --- |
| 1 | `chore: 初始化工程与 CI 骨架` | Cargo.toml、lib.rs、ci.yml、LICENSE |
| 2 | `feat(memory): 地址类型与 64 MiB 模拟物理内存` | memory.rs + 单元测试 |
| 3 | `feat(frame): 栈式帧分配器与 FrameTracker RAII` | frame.rs + 测试 |
| 4 | `feat(paging): Sv39 页表 map/unmap/translate` | paging.rs + 测试 |
| 5 | `feat(cli): 交互式命令与表格渲染` | kernel.rs / repl.rs / ui.rs |
| 6 | `feat(lab): lab2/lab3 实验脚本与 tour 回放` | lab 脚本 + examples/tour.txt |
| 7 | `docs: 实验指导书与设计文档` | docs/*.md |
| 8 | `test: 端到端测试与边界用例` | tests/cli.rs、补测试 |
| 9 | `chore(release): v0.1.0 第一阶段交付` | 版本号、CHANGELOG |
| 10 | `feat: 第二阶段……` | 后续迭代 |

建议每次提交都跑 `cargo test`，并在提交信息里写清"做了什么、为什么"。
评委会看提交粒度与信息质量，这比提交次数更能说明问题。

## 9. 答辩 Q&A 预演

| 问题 | 回答要点 |
| --- | --- |
| 为什么不直接改 rCore，而要做用户态模拟？ | 降低调试门槛；先建立正确心智模型，再进内核；两者用同一套 PTE/位域 |
| 页表在用户态模拟，怎么保证和真机一致？ | PTE 布局、Sv39 位域、三级索引、A/D 位都按规范实现，并逐级读内存 |
| 为什么用 Rust？C 不行吗？ | 所有权把"谁负责 free"变成类型问题；`!Clone` 直接消灭双重释放 |
| 和 rustlings 有什么区别？ | rustlings 练语法；本项目把语法落到内核资源生命周期上 |
| 实验怎么评分？ | 指导书给出四个实验 + rubric；`cargo test` 与 `tour.txt` 可自动判定 |
| 工作量是不是太小？ | 第一阶段已含分配器、页表、命令层、36 个测试；路线图有明确增量 |
| 评委没有 Rust 环境怎么办？ | 零依赖 + Dockerfile + 预编译二进制 + 录屏 |
| 引用 rCore 代码了吗？ | 只参考设计，未复制代码；文档逐条标注对照的源文件与函数 |
| 下一步做什么？ | Lab4 任务切换可视化、COW、闯关模式、与真实内核联动 |
| 怎么证明学生用了有效果？ | 试用记录：人数、耗时、卡点、改进前后对比 |
