【RAII】Drop 自动归还：没有显式 free，也不会忘记 free

  // 进入作用域，分配 2 帧
  let _a = FrameTracker::alloc(&fa)?;

> demo move
【move】所有权转移：一块物理帧只能有一个主人

  let frame = FrameTracker::alloc(&fa)?;   // 拿到 PPN 0x8_0009
  let moved = frame;                        // 所有权转移，frame 立刻失效
  // println!("{:?}", frame);            // ← E0382: use of moved value

  转移之后：moved 持有 PPN 0x8_0009，分配器持有 10 帧。
  drop(moved);                              // 离开作用域，帧自动归还
  分配器持有 9 帧（演示前 9 帧）。

对照 rCore：`PageTable::new` 会**拿走**一个 `FrameTracker` 作为根页表。
交出之后调用者手里就没有句柄了，所以绝不可能出现两个所有者各 free 一次。

> demo clone
【Rc】共享所有权：最后一个引用消失时才回收

  let a = Rc::new(FrameTracker::alloc(&fa)?);  // PPN 0x8_0009，strong_count = 1
  let b = Rc::clone(&a);                       // strong_count = 2
  两块"变量"指向同一帧，但物理帧仍然只有一份。分配器持有 10 帧。

  drop(b);                                     // strong_count = 1，帧还没回收
  分配器持有 10 帧。
  drop(a);                                     // strong_count = 0，此刻才真正 free
  分配器持有 9 帧（演示前 9 帧）。

对照 rCore：fork 之后的写时复制（COW）会让父子进程共享同一批物理页。
用 `Arc<FrameTracker>` 记录引用数，最后一个持有者析构时才归还帧 —— 这就是
Lab3 里 COW 实验能够安全实现的基础。

> demo double-free
【双重释放】为什么 safe Rust 写不出来

    let a = FrameTracker::alloc(&fa)?;
    let b = a;      // 移动：a 失效
    drop(a);        // ← E0382: use of moved value
    drop(b);        // 如果上面能编译，这里就会 double free

rCore 的 `FrameTracker` 没有实现 `Copy`/`Clone`，所以同一物理帧在同一时刻
只可能有一个所有者。需要共享时用 `Arc` 增加引用计数，由最后一个持有者
负责释放 —— 引用计数把"谁负责 free"变成了类型系统能检查的问题。

这正好解释了 rCore 的两个设计选择：
1. `FrameTracker: !Clone` —— 独占所有权；
2. `Arc<FrameTracker>` —— 共享所有权，计数归零才 Drop。
